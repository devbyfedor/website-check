# D1: tables and the free-plan budget

Session A5 part 2 (23.11.2026). Migration: `worker/migrations/0001_initial.sql`; since session fix-a2 also `0002_scan_mode.sql` (the column `scans.mode`, `full` or `quick`, written with the report in the same statement, so no extra row is written), since session fix-a4 `0003_rate_daily.sql` (the table `rate_daily`), and since session fix-a5 `0004_rate_state.sql` (`rate_events` and `rate_daily` replaced by `rate_state`) and `0005_scans_in_progress.sql` (a partial index of the scans in progress). ## Tables

- `sites`: one row per normalized address (scheme, host, "/"), the key of the 24-hour cache.
- `scans`: one row per scan: random id, site, `created_at` (the date by which old reports are deleted), status (`queued`, `running`, `done`, `error`), the report state, the country and data center of the browser, and the report JSON as text (the Worker returns it without parsing).
- `findings`: every item of a report that is not a pass (finding, manual check, hint, not checked), one row each, at most 60 per scan.
- `network_requests`: one row per host of a scan (request count, first start, last end, before the banner), at most 100 per scan. Not one row per request: a page makes 70 to 1,000 requests.
- `leads`: table only, for the lead form of stage C; columns provisional.
- `rate_salts`: the random salt of each UTC day; the salts of earlier days are deleted with the first scan of a new day and by the hourly cron cleanup. A start that crosses midnight keeps the newest salt: a salt is never created for a day that has a salt of the same or a later day.
- `rate_state` (since fix-a5, review findings 89 and 91): one row per visitor and UTC day: the hash of the visitor's address (IPv4, or the /56 of IPv6), the day, and the visitor's state encrypted (AES-GCM, key derived from the secret and the day's salt, padded to 1,024 characters before encryption): the times of the scans and starts of the last hour and the counts of the day (5 scans per hour, 15 per day; 20 starts per hour, 60 per day, a start answered from the cache included). The hash is an HMAC keyed with the secret `RATE_LIMIT_SECRET` of the scan Worker over the day's salt and the address, so the database alone is not enough to try all IPv4 addresses against it. No time of a visitor is stored in plain form, so a copy of the database (an export, or a Time Travel restore) cannot be joined with the creation times of the scans; it shows only that a pseudonym of the day used the service. What still links: a series of restores minute by minute shows which row changed when a scan appeared, and on a day with a single visitor every scan of the day is that visitor's (`docs/decisions.md`, fix-a5). Rows of earlier days are deleted with the first start of a new day and by the hourly cron cleanup. No raw address anywhere. Without the secret the API starts no scan and answers no start from the cache (HTTP 503).
- Until fix-a5: `rate_events` (hash and millisecond time of every scan, which equalled `scans.created_at`) and `rate_daily` (hash, day and count); both are dropped by migration 0004.
- Index `scans_in_progress` (since fix-a5, review finding 42): `created_at` of the scans that are `queued` or `running`, so the hourly cleanup of stuck scans reads those few rows instead of the whole table.

Foreign keys are on in D1; deleting a scan deletes its findings and hosts (`ON DELETE CASCADE`).

## Free plan (Cloudflare docs, checked 23.11.2026)

From https://developers.cloudflare.com/d1/platform/pricing/ and https://developers.cloudflare.com/d1/platform/limits/: 5 million rows read and 100,000 rows written per day, reset at 00:00 UTC; "Write operations include INSERT, UPDATE, and DELETE"; "Indexes will add an additional written row when writes include the indexed column"; at the limit "you will not be able to run queries against D1" until the reset. Maximum database size 500 MB on the free plan (5 GB per account); row or string at most 2 MB; 100 bound parameters per statement; 50 queries per Worker invocation (a `batch` counts as one); statements of at most 100 KB.

## Rows written per scan

Measured on the local D1 (the runtime of `wrangler dev`) by `worker/test/d1-budget.test.ts`, from `meta.rows_written` of every statement:

- Cache lookup: 0. A refused address (HTTP 400), a start beyond the visitor's start budget (HTTP 429 `starts`) and every start after the queue's day cap (HTTP 503 `daily-limit`) write nothing.
- Every other start writes the visitor's row once (since fix-a5): a start answered from the cache 1, a start refused by the hourly or daily scan limit 1 (the start counts, finding 89), a new scan 1 (the start and the slot in one write); the row is deleted once after its day. The budget counts as many cached answers per day as scans, 2 rows each.
- New site and scan: 6 (site row and its unique index; scan row, its primary key index, the index on site and date, and the partial index of scans in progress). An existing site: 4.
- Scan starts running: 2 (the scan row and its entry in the partial index).
- Report saved: 1 for the scan row plus one per finding row and one per host row.
- Retention delete: one per deleted row (scan, findings, hosts, site). The local runtime counts a deleted row once; the pricing page says writes to indexed columns add a row per index, so the budget counts 3 more for the indexes of scan and site.
- Salt: 1 per day, and 1 for deleting the salt of the day before. The hourly cleanup deletes only rows that would be deleted anyway, so it adds no rows; it reads the two small rate-limit tables and, by the partial index, the scans in progress, 24 times a day (before fix-a5 it read every row of `scans`, review finding 42).
- Two starts of the same address at the same moment: the second visitor gets the first scan and its slot is given back (1 more row, the visitor's row, only in that case).

Per scan, at the caps of the report (60 findings, 100 hosts), measured in fix-a5: 336 rows (visitor row 1 and its deletion 1, site and scan 6, running 2, report 161, retention delete with the indexes 165). With the median of the 30 saved captures (8 findings, 5 hosts in the test; measured 7.5 and 5): 42 rows.

At 80 scans per day, with 20 rows per scan kept free (progress of the scan screen, a retry), the daily salt and 80 starts answered from the cache: 80 × (336 + 20) + 2 + 160 = 28,642 rows at the caps, 5,122 at the median. Fedor's limit is a third of 100,000, 33,333 rows: both fit; the caps fit with 4,691 rows to spare. Every report deleted by the retention rule costs about as many rows as it cost to write, so the budget already counts the steady state in which old reports are deleted as fast as new ones arrive.

Reads: a status request reads one row, a cache lookup a few; the scan screen polling every second for 30 seconds reads about 30 rows per scan, far from 5 million per day.

## Size

The report JSON of the 30 saved captures (`npm run report:check`, no site visited): median 13.7 KB, mean 14.6 KB, max 41 KB; the builder refuses a report above 400,000 characters. At 80 scans per day that is about 1.2 MB per day at the mean and 3.3 MB at the largest real report, so the free plan's 500 MB per database hold about 400 days at the mean and about 150 days if every report were as large as the largest. Fedor's retention period (stage C) should stay below that, for example 90 days.
