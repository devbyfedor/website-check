# D1: tables and the free-plan budget

Session A5 part 2 (23.11.2026). Migration: `worker/migrations/0001_initial.sql`; since session fix-a2 also `0002_scan_mode.sql` (the column `scans.mode`, `full` or `quick`, written with the report in the same statement, so no extra row is written). Access: `worker/src/db/store.ts` and `worker/src/api/rate-limit.ts`. Local only so far: `npx wrangler d1 migrations apply website-check --local -c worker/wrangler.jsonc`; the database id in `worker/wrangler.jsonc` is a placeholder until Fedor creates the real database before the first deploy.

## Tables

- `sites`: one row per normalized address (scheme, host, "/"), the key of the 24-hour cache.
- `scans`: one row per scan: random id, site, `created_at` (the date by which old reports are deleted), status (`queued`, `running`, `done`, `error`), the report state, the country and data center of the browser, and the report JSON as text (the Worker returns it without parsing).
- `findings`: every item of a report that is not a pass (finding, manual check, hint, not checked), one row each, at most 60 per scan.
- `network_requests`: one row per host of a scan (request count, first start, last end, before the banner), at most 100 per scan. Not one row per request: a page makes 70 to 1,000 requests.
- `leads`: table only, for the lead form of stage C; columns provisional.
- `rate_salts`: the random salt of each UTC day; the salts of earlier days are deleted with the first scan of a new day and by the hourly cron cleanup.
- `rate_events`: one row per started scan with the hash of the visitor's address (IPv4, or the /56 of IPv6) and the time; rows older than an hour are deleted on the next start and by the hourly cleanup. The hash is an HMAC keyed with the secret `RATE_LIMIT_SECRET` of the scan Worker (since A5 part 5 the start of a scan runs in its queue object) over the day's salt and the address, so the database alone (an export, or a Time Travel restore of a deleted salt) is not enough to try all IPv4 addresses against it. No raw address anywhere. Without the secret the API starts no scan (HTTP 503).

Foreign keys are on in D1; deleting a scan deletes its findings and hosts (`ON DELETE CASCADE`).

## Free plan (Cloudflare docs, checked 23.11.2026)

From https://developers.cloudflare.com/d1/platform/pricing/ and https://developers.cloudflare.com/d1/platform/limits/: 5 million rows read and 100,000 rows written per day, reset at 00:00 UTC; "Write operations include INSERT, UPDATE, and DELETE"; "Indexes will add an additional written row when writes include the indexed column"; at the limit "you will not be able to run queries against D1" until the reset. Maximum database size 500 MB on the free plan (5 GB per account); row or string at most 2 MB; 100 bound parameters per statement; 50 queries per Worker invocation (a `batch` counts as one); statements of at most 100 KB.

## Rows written per scan

Measured on the local D1 (the runtime of `wrangler dev`) by `worker/test/d1-budget.test.ts`, from `meta.rows_written` of every statement:

- Cache lookup: 0. A cache hit, a refused address (HTTP 400) and a refused rate limit (HTTP 429) write nothing.
- Rate limit: 1 (the event), and 1 later when it is deleted.
- New site and scan: 5 (site row and its unique index; scan row, its primary key index and the index on site and date). An existing site: 3.
- Scan starts running: 1.
- Report saved: 1 for the scan row plus one per finding row and one per host row.
- Retention delete: one per deleted row (scan, findings, hosts, site). The local runtime counts a deleted row once; the pricing page says writes to indexed columns add a row per index, so the budget counts 3 more for the indexes of scan and site.
- Salt: 1 per day, and 1 for deleting the salt of the day before. The hourly cleanup deletes only rows that would be deleted anyway, so it adds no rows; it reads the two small rate-limit tables 24 times a day.
- Two starts of the same address at the same moment: the second visitor gets the first scan and its slot is given back (1 more row, only in that case).

Per scan, at the caps of the report (60 findings, 100 hosts): 1 + 5 + 1 + 161 + 1 + 165 = 334 rows. With the median of the 30 saved captures (8 findings, 5 hosts in the test; measured 7.5 and 5): 40 rows. The largest real capture (23 findings, 28 hosts) gives 116 rows.

At 80 scans per day, with 20 rows per scan kept free for part 3 (progress of the scan screen, a retry) and the daily salt: 80 × (334 + 20) + 2 = 28,322 rows at the caps, 4,802 at the median. Fedor's limit is a third of 100,000, 33,333 rows: both fit; the caps fit with 5,011 rows to spare. Every report deleted by the retention rule costs about as many rows as it cost to write, so the budget already counts the steady state in which old reports are deleted as fast as new ones arrive.

Reads: a status request reads one row, a cache lookup a few; the scan screen polling every second for 30 seconds reads about 30 rows per scan, far from 5 million per day.

## Size

The report JSON of the 30 saved captures (`npm run report:check`, no site visited): median 13.7 KB, mean 14.6 KB, max 41 KB; the builder refuses a report above 400,000 characters. At 80 scans per day that is about 1.2 MB per day at the mean and 3.3 MB at the largest real report, so the free plan's 500 MB per database hold about 400 days at the mean and about 150 days if every report were as large as the largest. Fedor's retention period (stage C) should stay below that, for example 90 days.
