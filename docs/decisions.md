- 19.11.2026: name Website-Check DE. Folder, repository and address: `website-check`.
- 19.11.2026: the repository is public from day one. Results of scans of real third-party websites never go into the repository.

- No date given in the brief (part of brief v1, 19.11.2026): explanations of findings are written in advance and stored in the repository. No AI generates findings or legal explanations at runtime.

Decisions made later in the sessions:

- 20.11.2026 (session A1, answer to the merge question): the manual Google Fonts check needs 5 findings, 3 are not enough. To reach 5, two test sites were replaced by sites of the same group that load Google Fonts; the replaced sites were the last ones of their group without any Google Fonts evidence, so the mix of the 30 sites stays the same.
- 21.11.2026 (session A2): A2 is split into two parts. Part 1: the Cloudflare capture adapter and a check on three sites of whether consent tools behave the same with the Cloudflare browser as with the local run. Part 2: banner probe fixes, the 12-site measurement, `docs/measurements/a2.md` with the plan recommendation, and the merge into `main`. Reason: the main risk is checked first: a consent tool that treats the Cloudflare browser differently (for example lets trackers run) would make the scanner report violations that real visitors from Germany never see.
- 21.11.2026 (answer about Microsoft Consent Mode): a Microsoft UET request before consent in Microsoft Consent Mode "denied" (`asc=D`) stays a finding, not "bitte manuell prüfen". Reason: the request to Microsoft before consent is an established fact, and the manual check is only for what the scanner cannot determine. The risk class follows the brief rule: `consent-required` if a source says that such requests need consent, otherwise `grey-zone`. The finding text will briefly explain the mode and what goes to Microsoft before consent (data change, source and draft text: `docs/backlog.md`).
- 21.11.2026 (session A2): a lab deploy is allowed if the Worker's CPU time on Cloudflare cannot be measured without a deploy. Only a separate Worker `website-check-lab` on workers.dev with only the measurement endpoint behind a token, no site and no data storage. The agent sets the token secret itself from `.dev.vars` and never prints its value. The Worker is deleted after part 2 of A2. Reason: the 10 ms CPU limit decides the plan, and it only applies when the Worker runs on Cloudflare.

- 21.11.2026 (before A2 part 2): A2 gets a third part. Part 2: capture inside a Durable Object in the EU jurisdiction and recognition of blocked pages; part 3: banner fixes, the 12-site measurement, `docs/measurements/a2.md`, the merge and deleting the lab Worker. Reason: the free plan allows only occasional overruns of the Worker's 10 ms CPU and stops constant overruns with error 1102, so "no request was stopped" in part 1 proves nothing; a Durable Object has 30 s CPU per request.
- 21.11.2026: the undocumented launch option for the browser's country is not tried. Reason: it can be removed without notice, so the product must not depend on it; the Netherlands are in the EU too and the banners behaved as from Germany. The browser location is checked through a Durable Object in the EU jurisdiction, which is documented.
- 21.11.2026: the state "Prüfung blockiert" for the user interface is built in B2 from existing elements and shown to Fedor (as in the brief). In A2 the scanner only has to recognise the blocking honestly.
- 21.11.2026: plain browser-protocol connection without Puppeteer only if the Durable Object does not work; Quick Actions are first checked in the documentation (all requests of the page and the main document headers) and measured only if they return both; the fixed 13 ms of strategy (b) are not investigated if the Durable Object works.

## Technical decisions

- 20.11.2026: the brief arrived as `docs/BRIEF.md` and is committed as `docs/brief.md`, because the brief and all instructions use that name and GitHub paths are case-sensitive.
- 20.11.2026: `.gitattributes` forces LF line endings, so Git on Windows (system `core.autocrlf=true`) never rewrites the read-only files in `design/`.
- 20.11.2026: Node 24.15.0 is pinned in `.nvmrc` and `.node-version`; `engines` allows `>=24.15.0 <25` and `.npmrc` sets `engine-strict`, so a wrong Node major fails at install. Node 24 is the installed LTS line.
- 20.11.2026: dependencies are saved with exact versions (`save-exact`) and `package-lock.json` is committed, so every session installs the same versions.
- 20.11.2026: TypeScript 6.0.3 (the last JavaScript-based release) instead of 7.0 (the native port): stage B uses Next.js and other tools that load the TypeScript JavaScript API; revisit when they support 7.
- 20.11.2026: no build step for TypeScript. Node 24 runs `.ts` files directly (type stripping), so the code uses only erasable syntax (`erasableSyntaxOnly`) and explicit `.ts` import extensions; Vitest and later wrangler read the same files.
- 20.11.2026: Vitest 5 with one project per workspace; `npm test` runs only unit tests without browser or network.
- 20.11.2026: registrable domains come from `tldts` with the private part of the Public Suffix List, as browsers do: every `*.myshopify.com` shop is its own site, and each `*.googleapis.com` host is its own site. `tldts` ships the list and runs in Node and in Workers.
- 20.11.2026: first party means the registrable domains of the final URL and of every earlier main document (HTTP redirects and client-side redirects), because the site owner controls those redirects.
- 20.11.2026: every third-party request belongs to exactly one service. Inside a third-party iframe, the outermost third-party iframe owns it; a request triggered by a script or stylesheet of an embedded product (map, video, chat, reviews, analytics, captcha, …; not fonts, CDNs, platforms, consent tools or tag managers) belongs to that product; a script of an unknown third party also owns what it triggers. Reason: Google Fonts loaded by the Google Maps script or inside a YouTube iframe does not mean that the site embeds Google Fonts; the product's entry lists such requests under "includes". This avoids false positives.
- 20.11.2026: a service is a finding only if at least one of its requests got a response. If all requests failed (for example a domain that no longer exists), it is shown as a hint.
- 20.11.2026: unknown third-party hosts are grouped by registrable domain and shown as grey-zone hints ("bitte manuell prüfen"), never as violations.
- 20.11.2026: the local adapter reads request initiators from the Chrome DevTools Protocol (best effort). The analyzer also works without them, which matters for the Cloudflare adapter in A2.
- 20.11.2026: the network counts as quiet when the load event has fired, no request is open and nothing started or finished for 1.5 s; WebSocket and EventSource connections do not count. Limits from the brief: 15 s waiting, 20 s per page.
- 20.11.2026: the local adapter uses the full Chromium of Playwright in the new headless mode (`channel: 'chromium'`), not the reduced headless shell, and a fresh browser context per site with service workers blocked, so every visit is a first visit without stored consent.
- 20.11.2026: the consent banner probe is one plain JavaScript string injected before any page script, so the Cloudflare adapter can reuse it unchanged. It checks known selectors every 100 ms and a text heuristic every 500 ms, and it only reads the page.
- 20.11.2026: rules data are JSON files in `scanner/data/`, validated when they are loaded; unit tests check that every cited source exists in `docs/rules-sources.md`.
- 20.11.2026: `npm test` runs only unit tests. The Playwright adapter has its own integration test (`npm run test:integration`) against a local fixture server; Chromium maps the fixture host names to 127.0.0.1, so no request leaves the machine.
- 20.11.2026: the local adapter sends the user agent of a normal desktop Chrome of the same version, never "HeadlessChrome". Reason (rules research, vendor code checked): Real Cookie Banner and Didomi accept all services for user agents containing "headless" by default, Usercentrics does so with its bot detection on, and Cookie Notice hides its banner and its blocking script. With a headless user agent the scan would see trackers that real visitors do not see before consent, which would be false positives. None of the 18 consent tools checked reads `navigator.webdriver`, so the adapter does not touch it. The scan sends no extra headers (no From, no Global Privacy Control).
- 20.11.2026: at the end of a visit the adapter reads, best effort, what Cookiebot (`Cookiebot.consent`) and Usercentrics (`UC_UI.areAllConsentsAccepted()`) report about consent (`consentBanner.signals`). The scan never consents, so a reported consent means automatic consent; the manual check uses it, the analyzer does not yet.
- 20.11.2026: Jimdo's built-in cookie banner has no documented element id; it is found by the generic text heuristic of the banner probe, not by a selector.
- 20.11.2026: rules data from a research run with adversarial verification (12 helpers): 95 services with 224 host patterns, 132 cited sources, every source opened twice, none rejected. Services whose loader can be used in a documented consent-respecting way (Klaviyo loader, HubSpot, Matomo Cloud, Mouseflow, etracker, Jetpack Stats, Tidio, Userlike) and all review widgets are grey-zone, because a request alone does not prove a violation. The catch-all entry for `www.google.com` and `www.gstatic.com` was dropped; such requests are reported as an unknown third party.
- 20.11.2026: `.gitignore` ignores `/local/` (the folder in the repository root) instead of `local/`, because the pattern without a leading slash also hid the code folder `scanner/src/local/`.
- 20.11.2026 (after the manual check, replaces the part of the attribution rule about products and unknown scripts): an embedded product owns only the requests to its own provider that it triggers in the page (Google Fonts loaded by the Google Maps script belong to Google Maps). Google Fonts loaded by an app or script of another provider stay a Google Fonts finding, with the initiator in the evidence, because the site installed and configured that app (the design reference says "Google Fonts kommen meist aus einer App"). Requests inside a third-party iframe still belong to that iframe's service. Found on a test site where a newsletter app injects its form fonts from Google.
- 21.11.2026 (A2 part 1): the Cloudflare adapter uses `@cloudflare/puppeteer` 2.0.1 (Puppeteer 25.10, the same Chrome 152 as Browser Run), not `@cloudflare/playwright`. Reason: with Playwright its whole server part runs inside the Worker and handles every protocol event, which costs Worker CPU; Puppeteer is lighter and still lets strategy (b) open a raw browser-protocol tab.
- 21.11.2026 (A2 part 1): strategy (a) records requests from Puppeteer's network events like the local adapter. Strategy (b) opens its own tab with `Target.createTarget` and enables only page lifecycle events, interception of document responses (`Fetch.enable` for `Document` at the response stage: status, headers and redirects of the main document) and auto-attach for out-of-process iframes; it never enables network events and reads all requests with one Resource Timing call at the end. Reason: (b) is the "more work in the page" variant (plan C) and must keep the messages to the Worker as few as possible.
- 21.11.2026 (A2 part 1): both strategies present the same visitor as the local Playwright adapter: the browser protocol commands are copied from Playwright 1.65 (user agent of a desktop Chrome on Windows with the same client hints and `Accept-Language: de-DE`, locale override `de-DE`, time zone `Europe/Berlin`, viewport and screen 1440 x 900, focus emulation), defined once in `worker/src/capture/emulation.ts`, and the shared values in `scanner/src/capture/settings.ts`. Checked with plain `wrangler dev` against a local fixture site: the fixture server received the same `Accept-Language`, `sec-ch-ua-platform` and user agent from all three, also inside a cross-site iframe.
- 21.11.2026 (A2 part 1): in strategy (b) the browser hides the HTTP status of cross-origin resources without CORS (`responseStatus` 0) and also lists some failed requests, so a third-party response cannot be confirmed; the analyzer then shows those services as hints, not findings. Kept as it is (no rule change in part 1): it is a measured limit of strategy (b) for the plan decision.
- 21.11.2026 (A2 part 1): the lab Worker has its own config `worker/wrangler.lab.jsonc` (name `website-check-lab`, workers.dev only, no preview URLs, Workers Logs and traces explicitly off, browser idle timeout 10 s, the minimum). Dev-only switches (`LAB_ALLOW_LOCAL`, `LAB_TRACE_URL`) exist only in `worker/.dev.vars`; on Cloudflare the endpoint refuses local and private host names.
- 21.11.2026 (A2 part 1): the lab deploy was needed: the Cloudflare docs give a Worker's CPU time only for deployed Workers (Workers Logs, Tail Workers and Logpush, the last two paid; real-time logs), limits are not enforced in local development, and `wrangler dev --remote` documents no CPU time. CPU and wall time per request come from `wrangler tail`, filtered by `scanner/src/local/tail-filter.ts` so that no header (and no token) reaches a file.
- 21.11.2026 (A2 part 2, narrowed after the review): a page counts as a check page (`blocked`) only when it is almost empty (at most 600 characters of text, 3 links and 15 requests), does not say that it redirects the visitor, and either its whole title is a "please wait" phrase ("Einen Moment bitte …", "Bitte warten", "One moment, please") or its text says that the request or the browser is being checked ("während Ihre Anfrage geprüft wird", "Ihr Browser wird überprüft", "Checking your browser", …). Reason: the check page of Site 06 has HTTP 200, a German title, 53 characters and 2 requests, and a normal homepage taken for a check page would hide its findings. So a title that only starts with such words ("Sicherheitsprüfung & HU – Kfz-Prüfstelle …") does not count, nor does "Ihre Anfrage wird geprüft" alone (a thank-you page after a contact form says it too). With HTTP 503 the same rule applies, a 503 maintenance page stays an HTTP error. The reason text names the rule and the sizes, never the title (a check page title is often the domain). Checked on all 72 saved captures (A1 and A2), no site visited: exactly the 2 Cloudflare captures of Site 06 change to `blocked`.
- 21.11.2026 (A2 part 2): `analyzeCapture` is the one entry point of the analysis: a capture that is blocked or failed gives the state and no analysis at all, so a check page can never look like a clean site. It decides saved captures again (`recheckCapture`), so captures saved before a rule follow it.
- 21.11.2026 (A2 part 2): the scanner does not hide that it is an automated browser. The check of Site 06 reports the failed check `webdriver` in its own check request, and Cloudflare documents that Browser Run "requests are always identified as bot traffic". Hiding `navigator.webdriver` or similar to get past a site's bot protection would be evasion of that protection; the honest answer is "Prüfung blockiert".
- 21.11.2026 (A2 part 1): Site 06 was replaced by Site 14 for the three-site check, because its web host answers the Cloudflare browser with a bot check page; the rule of the session message says to record such a site and take another. The replacement needed a second, short browser session (9.3 s), because the first one had already been closed right after its last page.
- 21.11.2026 (A2 part 2): the lab capture runs in one Durable Object `LabBrowser` (SQLite class, as the free plan requires, through the `migrations` entry `new_sqlite_classes` as in Cloudflare's guide) reached through `LAB_BROWSER.jurisdiction("eu")`. The Worker in front only checks the token and passes the request on without parsing the answer. Reason: a Durable Object ran 1.5 s and 5 s of CPU per request on the free plan without being stopped (step 1), and the jurisdiction is the documented way to keep the object in the EU.
- 21.11.2026 (A2 part 2): the object keeps the browser in memory between requests and reuses it while it is connected, as in the guide; unlike the guide it closes the browser as soon as the driver asks, keeps the browser's idle timeout at the minimum of 10 s, and closes a forgotten browser with an alarm after 30 s without a job. Reason: the free plan has 10 browser minutes per day, and an open browser keeps using them.
- 21.11.2026 (A2 part 2): Quick Actions are not measured. Reason: by their documentation (every endpoint of developers.cloudflare.com/browser-run/quick-actions/ and its API reference) none returns the requests a page made; they return only the main document's status and headers. A capture of third-party requests is impossible with them.
- 21.11.2026 (A2 part 3, Fedor's decision): hosts on Google's country domains count as the same host on google.com (`www.google.it/ads/ga-audiences` is the same service as `www.google.de/...` and `www.google.com/...`). The list of 186 country domains is Google's own (https://www.google.com/supported_domains, fetched 21.11.2026, stored in `scanner/data/google-domains.json`); the rules data names only google.com, and a pattern on a country domain is an error. Reason: the Cloudflare browser runs in different EU countries (Netherlands in part 1, Italy in part 2), and Google answers it on the domain of that country, so the same visit would otherwise give different services or unknown hosts.
- 21.11.2026 (A2 part 3): the banner probe follows a hit into open shadow roots and back out through the host, reads `aria-label`, checks two more points 3 % from the top and bottom edge, and accepts bars from 36 px height; Cookie Notice is found by `#cookie-notice` alone. Reason: on the saved screenshots of the 30 sites four visible banners were missed: two Shopify consent dialogs drawn in the open shadow root of a zero-size element, one top bar in the open shadow root of an empty wrapper, and one 70 px Cookie Notice bar below the lowest probe point (with classes `cn-bottom` instead of `cn-position-*`). Closed shadow roots stay unread; no such banner was seen.
- 21.11.2026 (A2 part 3): the comparison of a cloud capture with the local one leaves CORS preflight requests (initiator `preflight`) out of counts, hosts and completeness and counts them apart. Reason: Puppeteer reports a preflight as a request of its own, Playwright does not, and the request it prepares is in both captures. The capture itself keeps them; whether a preflight alone may make a service a finding is not decided yet (see `docs/backlog.md`).
