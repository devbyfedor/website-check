## 3. The error text of `fetch` in a Worker

A lab route of the pages Worker (`/lab/fetch-errors`) with fixed addresses only: our own host and documented addresses, no host of anyone else. Each address once with a raw `fetch` (timeout 8 s) and once through the product's `probeHttps` (the guard replaced for these fixed addresses).

- Cloudflare: no address gave an exception. Cloudflare answered itself with an HTTP error page (`server: cloudflare`, body "error code: NNNN") in 1 to 10 ms:
  - `https://127.0.0.1/`, `https://[::1]/`, `https://localhost/`, `https://192.0.2.1/` (RFC 5737) and `https://[2001:db8::1]/` (RFC 3849): HTTP 403, error code 1003;
  - our own lab host on port 444: HTTP 404, error code 1042;
  - `https://refused.invalid/` (RFC 2606): HTTP 530, error code 1016.
  `probeHttps` gave `http-error` with that status each time; the HTTPS row of a report is then "bitte manuell prüfen" (`httpsCheck`: only `answers`, `refused` and `redirects-to-http` decide).
- Plain `wrangler dev` on the laptop (workerd): the closed ports (127.0.0.1, ::1, localhost, our host on port 444) threw "Error: Network connection lost." after about 2 s (`isConnectionFailure` yes, `probeHttps` `unavailable`); 192.0.2.1 timed out after 8 s; 2001:db8::1 "Network connection lost." after 44 ms; the `.invalid` name "internal error; reference = …" (`isConnectionFailure` no).
- So on Cloudflare the outcome `refused` (and with it "ohne HTTPS" from a refused https:// address) did not arise for any address we may use. A refusal by a host outside Cloudflare could not be produced: Cloudflare refuses IP addresses (1003) before any connection, and our own hosts are Cloudflare's. Whether a real refused connection comes as an exception or as a Cloudflare error page stays open; in both cases the report says "bitte manuell prüfen".
- On the side: the scan Worker's quick checks of the lab pages Worker's host (another Worker of the same account on workers.dev) worked, 16 of 16 (9 of the HTML reader, 7 of the CPU rounds); the 1042 above came from a Worker asking its own host on port 444.
